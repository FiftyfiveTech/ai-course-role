# ROLE-019 — Phase 1 drift findings

## Grid

3 personas x 2 difficulty levels, all 6 cells run fresh with live Groq calls
(`openai/gpt-oss-120b`), no mocked or reused sessions:

| Persona | Scenario | Difficulty |
|---|---|---|
| Alex | order-change | easy, hard |
| Jordan | billing-dispute | easy, hard |
| Sam | delivery-delay | easy, hard |

Each cell: 1 opening + 10 scripted trainee turns = 11 persona turns, 21 total turns
(satisfies the >=20-turn requirement). `Controller` (ROLE-018) drives difficulty/mood as an
explicit state independent of the scenario's own YAML `difficulty` field.

Note on scope: the ticket's "5 test sessions" undercounts the 3x2 grid (6 cells). We ran
all 6 cells fresh, live, for both phases rather than trying to hit exactly 5 — see the
regex-bug finding below for why reusing any on-disk session would have been dishonest anyway.

## A bug found before the numbers could be trusted

The first BEFORE run flagged 1 `FACT_DRIFT(price_target)`, in `order-change / hard`. On
inspection, the flagged text was:

> "...from the SoundCore 2 (£49) to the SoundCore 3 (£69)..."

— factually correct, both prices right. The flag was a false positive: the `price_target`
contradiction regex in `scripts/drift_harness.py` was `£(?:39|49|79|89)\b`, which included
`49` — the *valid* `price_original` value. Any turn correctly stating both prices in one
sentence tripped it. Fixed by dropping `49` from that pattern (see `drift_harness.py`,
`FIXTURES["order-change"]`). All numbers below are from the re-run after the fix.

Separately: the 3 `sessions/drift_*.jsonl` files that predated this session (apparently left
over from ROLE-017) turned out to be generated by `test_drift_harness.py`'s mocked-Groq test,
not live runs — canned scripted text, not real model output. There was no genuine baseline to
reuse; both BEFORE and AFTER below are live, not test fixtures.

## The fix (applied regardless of the null result)

Added `{{PINNED_FACTS}}` — same mechanism as `{{CONTROLLER_STATE}}` (ROLE-018):
`PersonaAgent.set_facts()` in `src/role/persona.py` renders a short structured fact block
fresh into the system prompt each session, from the *same* `PersonaFacts.facts` dict
`drift_harness.py` checks contradictions against — facts-checked and facts-pinned can never
drift apart. All three prompts (`prompts/persona_v1.md`, `persona_billing_dispute_v1.md`,
`persona_delivery_delay_v1.md`) had their exact factual values (order numbers, prices, dates)
stripped out of the `## Situation` prose and moved into this pinned block.

We shipped this even though BEFORE showed no drift to fix, because:
- it is good practice independent of this measurement (matches the ROLE-018 pattern of
  moving ground truth out of prose the model must recall, into explicit rendered state)
- the ticket's done-when only requires recording drift count before AND after, not a
  demonstrated improvement

## Verdict

**Before: 0/66. After: 0/66. No change** — because there was nothing measurable to fix.
`openai/gpt-oss-120b` did not drift on facts, goal, or tone across any of the 6 cells at
21 turns each, with or without the pinned-facts block. We are not asserting the fix reduced
drift — it didn't need to, on this measurement. `scripts/run_drift_matrix.py`'s
`test_run_drift_matrix_after()` gate reflects this honestly: it asserts AFTER's drifted-turn
count does not *exceed* BEFORE's recorded count (0), not that it strictly decreases (which
would be unsatisfiable from a base of zero).

## Known limitation

A live pytest run of `test_run_drift_matrix_after()` (which re-runs the full 6-cell AFTER
matrix internally) hit a Groq free-tier rate limit after ~260 live calls accumulated across
this session's before/after/re-verification runs, and the arm-policy Ollama fallback failed
because Ollama is not running/configured in this dev environment (`404` at
`localhost:11434`). The numbers in this file come from two direct
`uv run python scripts/run_drift_matrix.py before|after` invocations, run once each,
which completed cleanly — they are not from the pytest wrapper. Re-running the gate
repeatedly in quick succession will reproduce the rate limit; space out reruns or configure
a real local Ollama fallback model before relying on the pytest gate in CI.

## What a future pass could try

0/66 with this scripted-reply harness at 21 turns may mean either (a) the persona model
genuinely holds up over this conversation length, or (b) the detector/scenario design isn't
adversarial enough to surface drift that's actually there (only 3-5 contradiction patterns
per persona, scripted trainee replies that don't actively probe recall). A stronger test
would extend turn count and add trainee turns designed to stress memory (asking the persona
to restate facts late in the conversation, introducing distractor information) before
concluding this persona doesn't drift.
